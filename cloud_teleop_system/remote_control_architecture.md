# 机器人超低延时云端遥控架构方案

基于现有的系统硬件（Jetson Orin NX + ROS 2 + FRCOBOT 机械臂 + Gemini 330 深度相机 + RK3588 + T113i），要实现跨越广域网（WAN）的超低延时云端遥控（Teleoperation），核心挑战在于克服网络抖动和丢包重传带来的延迟突刺。目标是将端到端（玻璃到玻璃）延迟控制在 **100ms - 150ms** 以内。

---

## 1. 核心技术痛点与选型

传统的基于 TCP 或原生 ROS2 DDS 广播的方案在广域网下存在严重的“TCP 队头阻塞（Head-of-Line Blocking）”问题，一旦发生轻微丢包，画面和指令都会出现严重卡顿。因此，**必须全面转向基于 UDP 的传输协议**。

### 1.1 视频流传输（下行）：WebRTC + NVIDIA 硬件加速
为了精准遥控机械臂，操作员需要极限低延迟的实时监控画面（包括 RGB 和深度图）。
*   **传输协议**：使用 **WebRTC**（底层基于 RTP/RTCP over UDP）。WebRTC 在遇到拥堵时会自动调节码率或丢弃旧帧（跳帧），确保显示的永远是最新画面。
*   **硬件压榨**：在 Jetson Orin NX 上，绝不能使用 CPU 进行软编码。必须利用内部的硬件编码器（NVENC）。
*   **技术实现**：通过 GStreamer 的 `webrtcbin` 插件结合 `nvv4l2h265enc` 硬件编码器，将 Gemini 330 的画面以 H.265 格式硬编码并在 10~20ms 内推送到 WebRTC 通道。
*   **预期效果**：广域网端到端视频延迟可稳定控制在 50~80ms。

### 1.2 控制指令传输（上行）：WebRTC DataChannel 或 Eclipse Zenoh
摇杆或键鼠的高频控制指令（如 100Hz）需要极高的吞吐率和极低的抗丢包延迟。
*   **方案 A：Eclipse Zenoh（推荐 ROS2 原生方案）**
    *   Zenoh 是专为机器人和边缘计算设计的新一代协议。通过在 Jetson 和云端/操作端运行 `zenoh-bridge-dds`，可以将本机的 ROS2 Topic 直接投射到云端。
    *   **优势**：极低的资源消耗，底层自动走 UDP 和高效路由，完美解决 ROS2 跨网段和内网穿透问题。
*   **方案 B：WebRTC Data Channel**
    *   与视频流复用同一条 WebRTC 通道，底层使用 SCTP 协议。
    *   **关键配置**：必须配置为 `ordered = false, maxRetransmits = 0`（即不可靠、无序传输）。因为即使丢弃 1、2 个控制包也毫无影响，但绝对不能重传旧的指令，否则机械臂会产生危险的滞后动作。

## 2. 机械臂控制策略优化（ROS2 安全机制）

在不稳定的 WAN 网络中，直接传递目标点存在巨大安全隐患。我们需要在 Jetson 端加入安全容错机制：

1.  **采用速度空间控制（MoveIt2 Servo）**
    *   **策略**：避免直接从云端下发“绝对坐标（Pose）”让机械臂规划（如果网断了机械臂会一直走到目标），而是下发连续的“笛卡尔空间速度向量”或“关节速度（Joint Velocities）”。利用 `frcobot_ros` 结合 MoveIt2 Servo 实现实时伺服控制。
2.  **死人开关与防失联急停（Watchdog）**
    *   **策略**：在 Jetson 的主控节点中设置一个软件看门狗。例如：如果超过 100ms 未收到云端最新的控制指令，立即将发布给 `frcobot` 的速度指令赋为 `0`（Stop）。防止因为网络突然断开，机械臂以旧速度继续移动撞毁物体。
3.  **信号平滑与插值（低通滤波）**
    *   **策略**：4G/5G 网络抖动可能导致云端指令频率从 100Hz 波动到 20Hz。在 Jetson 上接管指令并做一层插值（如低通滤波或卡尔曼滤波），让机械臂动作平滑，避免机械结构频繁受到冲击导致共振或损坏。

## 3. 云端基础设施架构（Cloud Infrastructure）

为连接局域网内的机器人主机与远端的操作者，云服务器不需要承担繁重的数据转发（尽量走 P2P），主要承担以下轻量级服务：

1.  **信令服务器（Signaling Server）**
    *   **用途**：用于在连接建立的初期，帮助 Jetson 和操控端交换 SDP（Session Description Protocol）信息（包含 IP、端口、编解码支持情况等）。用简单的 Node.js/WebSocket 或 MQTT 即可实现。
2.  **内网穿透服务器（STUN/TURN Server - Coturn）**
    *   **用途**：必须部署在具备静态公网 IP 的云服务器上。当机器人和操作员处于复杂的 NAT 网络（如双重路由器或移动基站后）无法建立 P2P 直连时，由 TURN 服务器负责高速中转 UDP 视频与控制流量。它是整套系统能随时随地连上的核心保障。

## 4. 实施路线建议

基于您目前的研发进度，推荐按以下步骤落地：

1.  **第一阶段：验证视频流延迟**。在 Jetson 上通过 GStreamer 搭建硬编 WebRTC 推流，在 Web 浏览器中用 JavaScript 拉流，评估 4G/5G 网络下的玻璃到玻璃延迟。
2.  **第二阶段：打通控制流**。使用 WebRTC DataChannel 将 Web 页面的摇杆数据发送到 Jetson，通过 ROS2 节点转换并订阅，打印延迟时间戳。
3.  **第三阶段：安全闭环**。加入 Watchdog 和 MoveIt2 Servo 速度控制，在虚拟环境或限制空间内测试断网情况下的机械臂保护机制，最后再进行真机高强度测试。
